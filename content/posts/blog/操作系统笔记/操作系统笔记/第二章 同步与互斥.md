### 并发进程/线程

在内存中同时存在的若⼲个进程/线程，由操作系统的<span style="color: #0b6e99;">调度程序</span>采⽤适当的策略将它(们)调度⾄ CPU上运⾏，同时维护他们的<span style="color: #0b6e99;">状态队列</span>。

- 多个并发进程/线程从<span style="color: #0f7b6c;">宏观</span>上是同时在运行；
- 从<span style="color: #0f7b6c;">微观</span>上看，他们的运⾏过程是**走走停停**；
- 并发的进程/线程之间是**交替执行**
  **并发进程之间的关系:**
- <span style="color: #6940a5;">独立关系</span>:并发进程分别在自己的变量集合上运⾏
- <span style="color: #6940a5;">交互关系</span>:并发进程执⾏过程中需要共享或是交换数据，交互的并发进程之间⼜存在着**竞争**和**协作**的关系 <span style="color: #e03e3e;">**竞争（RACE）**</span>:假设有两个进程在临界区会出现交汇，当红色小车先到达后，会在临界区设置⼀个⼩红旗，此时蓝色小车只能处于等待状态（waiting）

### 并发的好处以及带来的灾难

**好处:**

<details><summary><span style="color: #6940a5;">**允许同一时间间隔内运行多个应用**</span></summary>

并发使得操作系统能够在单个处理器上快速切换不同的任务，或者在多核或多处理器系统上同时执行多个任务。这意味着用户可以在同一时间间隔内启动和运行多个应用程序，比如同时编辑文档、浏览网页和听音乐。这种<span style="color: #0f7b6c;">多任务处理</span>提高了用户的效率和系统的灵活性。

</details>

<details><summary><span style="color: #6940a5;">**更好的资源利用率**</span></summary>

并发可以提高系统的<span style="color: #0f7b6c;">资源利用率</span>。例如，在一个单核CPU上，如果一个任务因为等待I/O操作（如从磁盘读取数据）而暂停，CPU可以在等待期间切换到另一个任务，而不是闲置。这样，CPU和其他资源（如内存、磁盘等）的使用更加高效，减少了资源的浪费。

</details>

<details><summary><span style="color: #6940a5;">**更好的平均响应时间**</span></summary>

由于任务可以交替执行，即使某些任务需要较长的处理时间，系统仍然可以快速响应用户的其他请求，例如采用<span style="color: #0f7b6c;">时间片轮转算法</span>。

</details>

**并发引发的灾难**

<details><summary><span style="color: #e03e3e;">**资源共享**</span></summary>

在并发环境中，多个线程或进程可能同时访问和修改相同的资源，如内存中的数据结构、文件或其他<span style="color: #e03e3e;">临界资源</span>（如打印机等）。如果没有适当的同步机制，这种共享可能导致数据的非预期修改，从而引起数据的不一致性和不可预测的行为。

</details>

<details><summary><span style="color: #e03e3e;">**竞争条件**</span>**（数据不一致性）**</summary>

竞争条件是指多个线程在没有适当<span style="color: #0b6e99;">同步</span>的情况下，同时尝试读取和修改同一个<span style="color: #e03e3e;">共享资源</span>，导致最终的资源状态取决于线程执行的精确时序（即运行结果与程序的运行顺序有关）。这种情况下的数据不一致性可能会导致严重的逻辑错误和安全漏洞。

</details>

<details><summary><span style="color: #e03e3e;">**饥饿与死锁**</span></summary>

- <span style="color: #e03e3e;">**饥饿:**</span> 当一个线程长时间得不到所需资源而无法继续执行时，就会发生饥饿。
- <span style="color: #e03e3e;">**死锁:**</span> 死锁是指两个或多个线程互相等待对方释放资源，从而导致它们都无法继续执行的情况。死锁通常发生在多个线程试图以不同的顺序获取多个锁时。

</details>

### 同步

由于异步会出现各种各样数据共享的问题，所以我们出现了同步机制。

**同步(Synchtonization) 指的是协调多个并发进程(或线程)的执行，使它们能够**安全地共享资源或进行通信。同步的目的是防止竞态条件、数据不一致和死锁等问题，从而确保系统的正确性和稳定性。下面会介绍一些同步工具。

## 同步与互斥的基本概念

<span style="color: #0b6e99;">协作进程</span>能与系统内的其他执行进程互相影响。例如同一进程内的线程可以直接共享<span style="color: #6940a5;">逻辑地址空间</span>(即代码和数据)，然而由于进/线程具有<span style="color: #e03e3e;">异步性</span>(各并发执行的进程以各自独立的、不可预知的速度向前推行)，可能导致数据的不一致。本节讨论多种机制，以便确保共享同一逻辑地址空间的协作进程/线程的<span style="color: #0f7b6c;">有序执行</span>，从而维护数据的一致性。

1. <span style="color: #e03e3e;">**临界资源**</span>:一个时间段内只允许一个进程使用的资源。许多物理设备(如摄像头、打印机)都属于临界资源，此外还有许多共享变量、数据、内存缓冲区等也属于临界资源。
2. <span style="color: #e03e3e;">**临界区**</span>:为了让进程单独使用资源而不受其他进程干扰而引入的概念，**临界区是进程中访问**<span style="color: #e03e3e;">**临界资源的那段程序(代码段)**</span>。我们希望这段代码是<span style="color: #0b6e99;">互斥</span>（mutual exclusion）的，也就是保证一个进/线程在临界区执行时，其他进/线程应被阻止进入临界区，即这段代码执行过程中最多只能有一个进/线程。
   ![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418456036-208f5075-fd6e-4ce1-8651-6f060add0d2f-944129.png)

对临界资源的互斥访问，在逻辑上分为四个部分:

```c
do {
    entry section;     //进入区，负责检查是否可进入临界区，若可进入，则应设置相关标志以阻止其他进程进入其临界区；以其他相关目标（可理解为"上锁"），以阻止其他进程同时进入临界区
    critical section;    //临界区；
    exit section;        //退出区；  负责解除正在访问临界区资源的标志（可理解为"解锁"）；
    remainder section;   //剩余区；  做其他处理
} while(true);
```

<span style="color: #0f7b6c;">**同步**</span>:亦称<span style="color: #0f7b6c;">**直接制约关系**</span>，指多个进程中发生的事情存在某种<span style="color: #e03e3e;">时序关系</span>，必须协同动作共同完成一个任务，简单来说是一种协作关系。

<details><summary>拓扑排序可以被视为一种同步机制或同步思想的应用。</summary>

拓扑排序解决的问题与同步的核心概念非常相似:确保任务按照正确的**时序关系**执行。根据你选择的内容，同步是指"多个进程中发生的事情存在某种**时序关系**，必须协同动作共同完成一个任务"。

拓扑排序正是处理这种时序关系的算法:

- 它为有向无环图中的所有顶点排序，使得对于图中的每一条有向边(u,v)，顶点u在排序中都出现在顶点v之前
- 这与进程同步中的"先后执行顺序"概念非常相似，即某些任务必须在其他任务之前完成
- 在操作系统中，拓扑排序可以用于任务调度，确保依赖关系得到满足，这本质上是一种同步机制

</details>

- 例如:工厂的流水线，每道工序都有自己特定的任务，前一道工序没有完成或不合格，后一道工序就不能进行；或者ABC三个进程分别负责输入、处理、输出数据，A必须先执行，B次之，C最后 <span style="color: #0b6e99;">**互斥**</span>:亦称<span style="color: #0b6e99;">**间接制约关系**</span>，指当一个进程访问某临界资源时，另一个想要访问该临界资源的进程必须等待。当前访问临界资源的进程访问结束并释放该资源后，另一个进程才能访问临界资源。

为了实现对临界资源的互斥访问，同时保证系统整体性能，需要遵循以下原则:

- <span style="color: #6940a5;">**空闲让进**</span>:临界区空闲时，可以允许一个请求进入临界区的进程立即进入临界区。
- <span style="color: #6940a5;">**忙则等待**</span>:即互斥访问，当有进程进入临界区时，其他试图进入临界区的进程必须等待。
- <span style="color: #6940a5;">**有限等待**</span>:对请求访问的进程，应保证能在有限时间内进入临界区(保证不会饥饿)。
- <span style="color: #6940a5;">**让权等待（可选）**</span>:当进程不能进入临界区时，应立即释放处理机（如主动阻塞），防止进程忙等。

### 实现临界区互斥的基本方法

### 软件实现方法

![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1747038427802-372e9fcb-bccf-4c93-abdc-700dd6094cd5-200820.png)

**如何判断软件实现方法是否遵循互斥四原则？**

- 判断是否遵循<span style="color: #0b6e99;">空闲让进</span>
  1. 观察是否有可能让表达式1与表达式2同时成立（<span style="color: #e03e3e;">potential deadlock situation</span>）
  2. 观察没有P1的情况下，P0能否通过循环进入临界区；没有P0的情况下，P1能否通过循环进入临界区
- 判断是否遵循<span style="color: #0b6e99;">忙则等待</span>
  - 当P0通过while循环但未进入临界区时切换到P1，检查P1能否也通过while循环；若可以，则不符合忙则等待（反向同理）
- 判断是否遵循<span style="color: #0b6e99;">有限等待</span>
  - 当P1处于临界区，P0卡在进入区通过不了while循环时，如果新来的P1进程可以比P0先进入临界区，则P0不满足有限等待，可能会发生饥饿
- 所有的软件实现方法**都不遵循让权等待**:进入区的`while(表达式);`含义是如果表达式为真，会一直执行循环，直到时间片到期被剥夺处理机或表达式为假；循环体为空语句，这就是所谓的<span style="color: #e03e3e;">忙等</span>

1. <span style="color: #0f7b6c;">单标志法</span>:两个进程互相授权使用临界区，一个进程访问完临界区后会把使用权交给另一个进程

```c
//共享整形变量标志
int turn = 0;
turn = 1; //表示允许进入临界区的是进程P1

/*进程P0*/
while(TRUE){
  //若turn等于本进程编号，准入临界区
  while(turn != 0);
  临界区；
  turn = 1;//允许对方进入临界区
  剩余区；
}

/*进程P1*/
while(TRUE){
  //若turn等于本进程编号，准入临界区
  while(turn != 1);
  临界区；
  turn = 0;//允许对方进入临界区
  剩余区；
}
```

- 满足<span style="color: #0b6e99;">忙则等待</span>

- <span style="color: #0b6e99;">空闲让进</span>:若P0不打算进入临界区，则`flag[0] == FALSE`，P1可通过while循环进入临界区
- <span style="color: #0b6e99;">忙则等待</span>:当P0、P1都希望进入临界区时，turn变量起作用，先申请的进程会被后申请的进程礼让（后申请的将turn置为先申请的进程编号）
- <span style="color: #0b6e99;">有限等待</span>:若P0在临界区，P1等待进入，当P0退出临界区后修改flag\[0]=FALSE，P1就能通过while循环进入临界区
- 不遵循<span style="color: #0b6e99;">让权等待（软件无法实现）</span>:进程即使进不去临界区，也会一直执行while循环空转直到时间片用完

<details><summary>解析:</summary>

本题考察Peterson算法。

算法实现互斥的主要思想在于设置了一个turn变量用于进程间的互相谦让。如果进程P0试图访问临界资源，则flag\[0]=true表示P0希望访问。此时如果进程P1还未试图访问临界资源，则flag\[1]在进程上一次访问完临界资源退出临界区后已设置为false。所以进程P0在直线循环判断条件时，第一个条件不满足，进程P0可以正常进入临界区，且满足互斥条件。

**需要考虑的是两个进程同时试图访问临界资源的情况**。注意turn变量的含义:当某进程试图访问时，首先设置自己的flag变量为true，表示希望访问；但又**设置turn变量为对方的进程编号，表示谦让**。因为在循环判断条件中turn变量不是自己的编号时就循环等待。虽然两个进程会互相谦让一番，但是这不会造成饥饿的局面，因为turn变量会有一个最终值，所以必定有进程可以结束循环进入临界区。

实际情况是，先作出谦让的进程先进入临界区，后作出谦让的进程则需要循环等待。其实这里可以想象为两个人进门，每个人进门前都会和对方客套一句“您走先”。如果进门时没别人，就当和空气说句废话，然后大步登门入室；如果两人同时进门，就互相“谦让”，但各自只客套一次，所以先客套的人请完对方，就等着对方请自己，然后光明正大进门。

Peterson算法遵循空闲让进、忙则等待、有限等待这三个原则，未遵循让权等待原则，暂时无法进入临界区的进程会占用CPU并执行拦截进入临界区的while循环导致忙等。

### 硬件实现方法

上面所述基于软件的解决方案(如<span style="color: #6940a5;">Peterson算法</span>)并不保证在现代计算机体系结构上正确工作，下面我们探讨临界区问题的多个解答，这包括内核开发人员和应用程序员采用的硬件和软件API技术。所有这些解答都是**基于**<span style="color: #e03e3e;">**加锁(locking)**</span>**为前提的，即通过加锁来保护临界区**。

首先我们介绍一些简单的<span style="color: #0b6e99;">硬件指令</span>(许多系统都具有的)，并有效地使用它们来解决临界区问题。另外，许多现代系统提供<span style="color: #0b6e99;">特殊硬件指令</span>，用于检测和修改字的内容，或者用于<span style="color: #e03e3e;">原子地</span>交换两个字(作为不可中断的指令)。我们可以采用这些特殊指令相对简单地解决临界区问题。通过硬件支持实现临界段问题的方法称为<span style="color: #0f7b6c;">低级方法</span>，或称<span style="color: #0f7b6c;">元方法</span>。

1. <span style="color: #e03e3e;">**中断屏蔽方法**</span>
   利用<span style="color: #0b6e99;">"开/关中断指令"</span>实现（与<span style="color: #0b6e99;">原语</span>的实现思想相同，即在进程访问临界区期间不允许被中断，从而避免进程切换，因此不可能出现两个进程同时访问临界区的情况）

进程切换通常是由<span style="color: #0b6e99;">中断指令</span>或者<span style="color: #0b6e99;">系统调用</span>触发，对于单处理机环境来说，在进入临界区时(例如修改共享变量)只要禁止中断出现，这样就能确保当前指令流可以有序执行，且不会被抢占。由于不可能执行其他指令，所以临界区不会被同时访问(共享变量不会被意外修改)。这种方法往往为<span style="color: #0f7b6c;">非抢占式内核</span>所采用。

```c
…
关中断
临界区
开中断
….
```

优点:<span style="color: #0f7b6c;">简单、高效</span>

缺点:

- 首先，这种方法要求我们允许所有调用线程执行<span style="color: #0b6e99;">特权操作</span>，因此只适用于<span style="color: #0f7b6c;">操作系统内核进程</span>，不适用于用户进程（因为开/关中断指令只能运行在<span style="color: #0b6e99;">内核态</span>，这组指令如果让用户随意使用会很危险，一个贪婪的程序可能在它开始时就调用`lock()`（即关中断）,从而独占处理器，更糟的情况是恶意程序调用`lock()`后，一直死循环）；
- **只能在**<span style="color: #e03e3e;">**单处理机环境**</span>**下使用**，在多处理机环境下这种解决方案不可行，如果多个线程运行在不同的CPU上，每个线程都试图进入同一个临界区，关闭中断也没有作用，线程可以运行在其他处理器上，因此能够进入临界区。

> 我们提到频繁禁用中断可能会影响系统的<span style="color: #0b6e99;">时钟</span>。解释为什么会发生这种情况，以及如何将这种影响降至最低。

> 系统时钟在每次<span style="color: #0b6e99;">时钟中断</span>时更新。如果中断被禁用，特别是长时间禁用，则系统时钟可能很容易丢失正确的时间。系统时钟也用于调度目的。例如，进程的时间量表示为时钟滴答数。在每个时钟中断时，调度器确定当前正在运行的进程的时间量是否已过期。如果时钟中断被禁用，调度程序将无法准确分配时间量。通过<span style="color: #0f7b6c;">仅在很短的时间内禁用</span>时钟中断，可以将这种影响降至最低。

1. <span style="color: #e03e3e;">**硬件指令方法**</span>

  <details><summary>`TestAndSet`**指令，**简称`TS`指令，也有地方称为`TestAndSetLock`指令，或`TSL`指令，或<span style="color: #e03e3e;">自旋锁</span>，`TSL`指令是用硬件来实现的，它的执行是<span style="color: #e03e3e;">原子的</span>，因此它的执行过程中不允许被中断，只能一气呵成，如果两个`TS`指令同时执行在不同CPU上，那么它们会按任意次序来顺序执行。</summary>

1. 从内存单元中读取值
2. 测试该值是否为1（然后返回真或假）
3. 内存单元值设置为1；
   该硬件指令**可适用于**<span style="color: #0f7b6c;">**共享内存的多处理机环境（SMP）**</span>\*\*，\*\*原理如下

- 测试并设置指令返回lock指向的旧值，同时更新新值，这些代码<span style="color: #e03e3e;">原子地</span>执行，因为既可以测试旧值又可以设置新值，所以把这条指令叫做"测试并设置"。
  ```c
  ```

//信号量共享变量lock表示当前临界区是否被加锁；
//true表示已上锁，false表示未上锁；
bool TestAndSet(bool \*lock){
bool old;
old = \*lock;      //old取存放lock原来的值；
\*lock = true;     //无论如何都给lock上锁，将lock设为true；
return old;       //返回lock原来的值；
}

//以下是使用TSL指令实现互斥的算法逻辑
while (TestAndSet(\&lock));     //"上锁"并"检查"
临界区；
lock = false;
remainder section;
\`\`\`

```
1. 如果刚开始`lock`值是`false`,则执行`TSL`后返回的`old`值也为`false`,并且给`lock`上了锁(`lock`值变为`true`)，然后`while`循环条件不满足，可以进入临界区，执行完之后给临界区解锁
1. 如果刚开始`lock`值是`true`，则执行`TSL`后返回的`old`值也还是`true`，`while`循环条件满足，则一直循环，直到当前访问临界区的进程在退出区将`lock`解锁或者等到时间片耗尽下处理机；
```

相比于软件实现方法，由于[双标志先检查法](/2accd32c4e888197a61de0b5a213d8a5#2accd32c4e88817fa144e0f94daa1135)无法做到先检查后上锁的一气呵成，因进程的异步性会发生许多错误，而TSL指令由于其<span style="color: #e03e3e;">原子性</span>把\*\*"上锁"和"检查\*\*"操作用硬件的方式变成了<span style="color: #e03e3e;">一气呵成的原子操作</span>，则避免了这种错误的发生。

  </details>

  <details><summary>`Swap`**指令**:有的地方也叫`EXchange`指令，或简称`XCHG`指令。`swap`指令是由硬件实现的，和`TSL`一样<span style="color: #e03e3e;">一气呵成</span>，执行过程不允许被中断。</summary>

逻辑上来看swap和TSL并无太大区别，都是先记录下此时临界区是否已经被上锁(记录在old变量上)，再将上锁标记lock设置为true，最后在检查old，如果old为false则说明之前没有别的进程，对临界区上锁后，跳出while循环进入临界区，执行完相应操作在退出区解锁。

  </details>

这两种硬件实现的优缺点

- 优点:实现<span style="color: #0f7b6c;">简单</span>，易<span style="color: #0f7b6c;">验证其正确性</span>，无需像软件实现方法那样严格检查是否会有逻辑漏洞；适用于<span style="color: #0f7b6c;">任意数目的进程</span>，不管是单处理机还是多处理机环境；可以支持进程内有<span style="color: #0f7b6c;">多个临界区</span>，只需为每个临界区设立一个布尔型变量。
- 缺点:不满足"<span style="color: #e03e3e;">让权等待</span>"原则，暂时无法进入临界区的进程会占用CPU并循环执行`TSL/Swap`指令，从而导致<span style="color: #e03e3e;">忙等</span>；从等待进程中随机选择一个进入临界区，有的进程可能一直选不上，从而导致"<span style="color: #e03e3e;">饥饿</span>"现象。

> 💡 这就是为什么后来发展出了**记录型信号量**和**条件变量**等机制，它们通过`block()`原语主动阻塞进程，真正实现了"让权等待"。

> 简而言之，虽然有其他调度方式可以剥夺忙等进程的CPU，但TSL指令本身的设计就是忙等的，这是其固有特性。

### 互斥锁

采用互斥锁保护临界区，一个进程在进入临界区时应得到锁；它在退出临界区时释放锁。

函数`acquire()`获取锁，而函数`release()`释放锁；

每个互斥锁有一个布尔变量`available`，表示锁是否可用。如果锁是可用的，调用`acquire()`会成功，且锁不可再用。

![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418456758-f2dee094-50c8-49ec-b896-48b2eb484544-047043.png)

互斥锁有<span style="color: #e03e3e;">两种类型</span>

1. **自旋锁**:当进程申请锁失败后，会一直循环申请锁，直到申请成功；

```c
struct Lock{    
  	bool available; //表示锁是否可用
}
```

  <details><summary>当进程申请锁失败后会处于什么状态呢？</summary>

就绪态/运行态

如果时间片没用完，则处于运行态，一直尝试获取锁；

如果时间片用完，则被剥夺处理机，处于就绪态；

注意哈，如果将其应用在<span style="color: #e03e3e;">单处理器上</span>，<span style="color: #e03e3e;">需要抢占式的调度器</span>(即不断通过时钟中断一个线程，运行其他线程)，否则自旋锁在单CPU上无法使用，因为一个自旋的线程永远不会放弃处理机。

  </details>

1. \*\*无忙等待锁:\*\*当进程申请锁失败后，会<span style="color: #e03e3e;">主动阻塞</span>自己，加入阻塞队列，让出处理机，这样就不会忙等了；等待其他进程释放锁之后，<span style="color: #e03e3e;">将其唤醒</span>加入就绪队列；
   上面的代码实现是有缺陷的，上锁时检查锁是否可用和上锁这之间如果发生进程切换，那么可能会违背忙则等待，让多个进程进入临界区，为此对`acquire()`或`release()`的调用必须原子地执行，因此，<mark style="background-color: #f4dfeb;">**互斥锁通常采用上面硬件实现方法所述的硬件机制来实现**</mark><mark style="background-color: #f4dfeb;">；</mark>
2. 采用中断机制，在获取锁之前关中断；不过该方式只对单处理机系统有效；
3. **原子操作指令**；

- **使用TSL指令实现自旋锁**

```c
struct Lock{    
		bool locked;
}

//获取锁
acquire(){    
		while(TestAndSet(locked));
}
```

如果锁被释放，那么TSL指令读取`false`并将`locked`值设置为`true`；

- 即锁被设置为忙，并且需要等待完成；
  如果锁处于忙状态，那么TSL指令读取`true`并将值设置为`true`；
- 不改变锁的状态并且需要一直循环；

```c
//释放锁
release(){   
		locked = FALSE ；
}
```

- **使用TSL指令实现无忙等待锁**

```c
struct Lock{    
		bool locked;    
		waitqueue q; //该锁对应的等待队列
}
```

**自旋锁特性总结:**

- **自旋锁**具有<span style="color: #e03e3e;">随机性</span>，不能保证进程按<span style="color: #0b6e99;">先来后到</span>的顺序使用CPU资源，顺序可能乱
- 需<span style="color: #e03e3e;">忙等</span>，**进程时间片**用完才下处理机，<span style="color: #e03e3e;">违反"让权等待"</span>
- 当进程在等待锁时，没有<span style="color: #0b6e99;">上下文切换</span>（上下文切换需要相当长的时间），因此在<span style="color: #0f7b6c;">多处理器系统</span>中，若上锁的时间短，则等待代价很低
- 常用于<span style="color: #0f7b6c;">多处理器系统</span>，一个核忙等，其他核照常工作，并快速释放临界区
- 不太适用于<span style="color: #6940a5;">单处理机系统</span>，忙等的过程中不可能解锁，因此**如果将其应用在单处理器上，需要**<span style="color: #e03e3e;">**抢占式的调度器**</span>\*\*（即不断通过时钟中断一个线程，运行其他线程），否则自旋锁在单CPU上无法使用，因为一个自旋的线程永远不会放弃处理机。\*\*即使有抢占式的调度器，性能开销也特别大，因为其他未持有锁的进程如果被调度的话都会在放弃CPU之前自旋一个时间片，浪费CPU周期
- 自旋锁不提供任何<span style="color: #0b6e99;">公平性</span>保证，实际上，自旋的线程在竞争条件下可能会永远自旋，可能会导致<span style="color: #e03e3e;">饿死</span>
  **无忙等待锁特性总结:**
- 由于<span style="color: #0b6e99;">等待队列</span>的存在，因此可以实现申请锁的进程的<span style="color: #0b6e99;">先来后到</span>，较为公平
- 未申请到锁时不需要忙等，但是需要<span style="color: #e03e3e;">阻塞自己</span>，切换其他进程，因此有一些<span style="color: #0b6e99;">切换上下文</span>的代价

【测试题】互斥锁是一种用于解决临界区互斥问题的常用手段，对`acquire()获取锁`或`release()释放锁`的调用必须<span style="color: #0b6e99;">原子地执行</span>，因此，互斥锁通常采用<span style="color: #0f7b6c;">硬件原语</span>（如`TestSet`指令或`exchange`交换指令来实现），对于TSL硬件原语实现的自旋锁与无忙等待锁，以下说法错误的是（）

<span style="color: #0f7b6c;">**A : 使用原子操作指令实现的互斥锁适用于单处理器或共享内存多处理器中任意数量的进程同步。**</span>

<span style="color: #0f7b6c;">**B : 自旋锁不能实现让权等待，但是阻塞锁可以**</span>

C: 自旋锁可以实现进程对临界区的先进先出（即按申请顺序访问临界区），不会导致进程饥饿

<span style="color: #0f7b6c;">**D: 互斥锁可用于多进（线）程之间，但是只能由获取锁的进（线）程对它进行解锁（即释放）；**</span>

<details><summary>解析</summary>

本题应该选择**C选项**；

首先，我们先了解一下什么是互斥锁，其实它就是一个普通的变量，可以是bool类型也可以是int类型（用0表示锁释放，1表示已上锁），上面这种实现出来的互斥锁，它是支持多临界区的互斥访问，什么意思呢，如果我们有好多个临界资源需要互斥访问，我们可以对它们分别实现一个互斥锁，即每把锁一个变量即可；注意，这个互斥锁变量，它是位于主存里的共享变量，不是某个进程私有的，否则实现不了一个进程拿到锁，别的进程进不去这种效果，因此我们说使用原子操作指令实现的互斥锁适用于单处理器或共享内存多处理器中任意数量的进程同步，因此A选项正确。

![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1747056353194-e41b7a1d-e183-4619-88ea-232ec5c7f4ba.png?x-oss-process=image%2Fformat%2Cwebp)

另外，我们要注意拿到锁和释放锁的必须是同一个进程，否则可能会出现A进程拿到锁之后，但是B进程却释放了这把锁，这时候C获取了这把锁，这样就不满足互斥进入临界区这个规则了，因此在拿到锁和释放锁的时候，需要验证一下身份，例如当某个锁是空闲的时候，A拿到了这把锁，这时候可以把A的进程pid记下来，之后释放锁的时候，验证一下pid是否相等，是的话才可以释放锁，这样就可以保证互斥访问临界区了，因此D正确；

BC选项的话，我们可以根据这两把锁的实现方式来看，**自旋锁**在拿不到锁的时候，并没有及时释放处理机，而是一直循环尝试是否可以获取锁，因此**不符合让权等待**，而阻塞锁在拿不到锁的时候，就将该进程加入阻塞队列里面，因此，**阻塞锁可以实现让权等待**，B 选项正确。此外由于自旋锁具有随机性，没有队列这种数据结构保证进程按照先来后到的顺序使用CPU资源，因此顺序可能会乱，另外如果当某个进程离开临界区时有多个进程等待进入临界区，就有可能导致某些进程由于每次临界区空闲的时候没有上处理机，或者轮到上处理机的时候，临界区有锁，从而导致饥饿，因此C选项错误。

扩展一下，以上这种使用原子操作实现的互斥锁还有可能导致**死锁**的发生，比如某个低优先级进程拿到了锁，在使用这把锁的时候，来了一个高优先级的进程获得处理机，并且它也想进入临界区，这时就发生了死锁。

### 信号量

我们刚刚讨论的<span style="color: #0f7b6c;">互斥锁</span>通常被认为是最简单的同步工具，接下来我们会介绍一个功能更强大的工具，它的功能类似于互斥锁，但能提供更为高级的方法，使进程能够进行同步活动。

用户进程可以通过使用操作系统提供的<span style="color: #0b6e99;">**一对原语**</span>来对<span style="color: #e03e3e;">**信号量**</span>进行操作，从而方便地实现进程同步与互斥。

<span style="color: #e03e3e;">**信号量**</span>本质上是一个<span style="color: #0b6e99;">**变量**</span>（可以是一个整数，也可以是更复杂的记录型变量），用来表示系统中某种资源的数量。例如:系统中只有一台打印机，就可以设置一个初值为1的信号量。

一对原语:<span style="color: #0f7b6c;">**wait(S)原语**</span>**和**<span style="color: #0f7b6c;">**signal(S)原语**</span>，可以把原语理解为我们自己写的函数，函数名分别为`wait`和`signal`，括号里的信号量S是函数调用时传入的参数。`wait`、`signal`原语常简称为`P`（荷兰语`proberen`，测试）、`V`（`verhogen`，增加）操作，因此也常写成`P(S)`、`V(S)`。

1. 整型信号量
   用一个<span style="color: #0b6e99;">整数型变量</span>作为信号量，用来表示系统中某种资源的数量。与普通整型变量的区别是:对信号量的操作只有三种，即<span style="color: #0f7b6c;">初始化</span>、<span style="color: #0f7b6c;">P操作</span>、<span style="color: #0f7b6c;">V操作</span>。

eg:某计算机系统中有一台打印机…

```c
int S = 1;                // 初始化整型信号量，表示当前系统中的打印机资源数

void wait(int S) {        // ‘wait’原语，简称“进入区”
  while (S <= 0);       // 如果资源不够就一直循环等待；“检查”和上锁一气呵成，避免并发、异步导致的问题，依旧有自旋的问题，不满足让权等待
  S = S - 1;            // 如果资源数够，则申请一个资源
  // 由于原子操作不允许中断，当原子操作无法完成时，会自动恢复到操作之前的状态，这两个动作是不可拆分的
}

void signal(int S){       // 使用完资源后，在退出区释放资源
  S = S + 1;
}

/* 进程 P 的使用示例 */
process P
{
  // ...
  wait(S);              // 进入区，申请资源
  使用打印机资源……   // 临界区，访问资源
  signal(S);            // 退出区，释放资源
  // ...
}
```

1. **记录型信号量**
   由于互斥锁和整型信号量存在<span style="color: #e03e3e;">"忙等"</span>问题，人们提出了<span style="color: #0b6e99;">"记录型信号量"</span>，用记录型数据结构表示信号量。这种方式需要修改<span style="color: #0f7b6c;">wait()</span>和<span style="color: #0f7b6c;">signal()</span>操作的定义:<mark style="background-color: #f4dfeb;">当进程执行</mark><mark style="background-color: #f4dfeb;">`wait()`</mark><mark style="background-color: #f4dfeb;">并发现信号量不为正时，该进程不再忙等待而是</mark><mark style="background-color: #f4dfeb;">**阻塞自己**</mark>。阻塞操作将进程放入与信号量关联的<span style="color: #0b6e99;">等待队列</span>中，并将进程切换为<span style="color: #0b6e99;">阻塞状态</span>。然后，控制权转交给CPU调度程序，选择其他进程执行。

因等待信号量S而阻塞的进程，在其他进程执行<span style="color: #0f7b6c;">`signal()`</span>操作后应被重新执行。进程重新执行通过<span style="color: #0f7b6c;">`wakeup()`</span>操作实现，该操作将进程从<span style="color: #0b6e99;">阻塞状态</span>改为<span style="color: #0b6e99;">就绪状态</span>，随后进程被添加到就绪队列中等待调度。

为此我们应该这样定义信号量及信号量操作:

```c
typedef struct(){
  int value;            // 剩余资源数
  struct process *list; // 指向等待进程链表中的指针
} semaphore;

/* 某进程需要使用资源时，通过 wait 原语申请 */
void wait(semaphore *S){
  S->value--;
  if (S->value < 0){
      add this process to S->list;
      block(); // 如果剩余资源数不够，使用 block() 原语使进程从运行态进入阻塞态，并将其挂入到 S 的等待队列（即阻塞队列）中
  }
}

/* 进程使用完资源后，通过 signal 原语释放 */
void signal(semaphore *S){
  S->value++;
  if (S->value <= 0){
      remove a process P from S->list;
      wakeup(P); // 释放资源后，若还有别的进程在等待该资源，则使用 wakeup 原语唤醒阻塞队列中的一个进程，将其从阻塞态变为就绪态
  }
}
```

- 在考研中`wait(S)`、`signal(S)`也可以记为`P(S)`、`V(S)`,这对原语可用于实现系统资源的“申请”与“释放”。
- 该机制由于调用了`block`原语将不能进入临界区的进程阻塞从而释放了处理机，\*\*因此遵循了“让权等待”这一原则，\*\*不会出现“忙等”现象。
- 注意该种机制实现的信号量可以是负数，而在具有忙等待的信号量经典定义(即整型信号量)中，信号量的值不能为负值。**如果信号量为负值，那么它的绝对值就是等待它的进程数。出现这种现象的原因是在实现wait()操作时**互换了递减和测试的顺序。

> 对`signal()`操作中`S->value <= 0`的解释例子

> 如果 `sem= 1`，有三个线程进行了 `P`操作:
>
> - 第一个线程 P 操作后，`sem`= 0；
> - 第二个线程 P 操作后，`sem` = -1；
> - 第三个线程 P 操作后，`sem` = -2；
>
> 这时，第一个线程执行 `V` 操作后， `sem`是 -1，因为 `sem`<= 0，所以要唤醒第二或第三个线程。

- 考试中出现`P(S)`、`V(S)`操作，除非特殊说明，否则默认S为记录型信号量.
  扩展:
- 通过为每个进程控制块<span style="color: #0b6e99;">`PCB`</span>的一个链接字段，等待进程的<span style="color: #0b6e99;">链表</span>可以轻松实现。每个<span style="color: #0b6e99;">信号量</span>包括一个<span style="color: #0b6e99;">整数</span>和<span style="color: #0b6e99;">PCB链表指针</span>。向链表中增加和删除进程以便确保<span style="color: #0b6e99;">有限等待</span>的一种方法是采用<span style="color: #0b6e99;">`FIFO`</span><span style="color: #0b6e99;">队列</span>，这里的信号量包括<span style="color: #0b6e99;">队列的首尾指针</span>。然而一般来说，**链表可以使用任何**<span style="color: #0b6e99;">**排队策略**</span>**，信号量的正确使用不依赖于信号量链表的特定排队策略。**
- <span style="color: #0b6e99;">**信号量操作需原子执行**</span>。要保证对同一信号量没有两个进程可以同时执行操作<span style="color: #0b6e99;">`**wait()**`</span>**和**<span style="color: #0b6e99;">`**signal()**`</span>**，这是一个临界区问题。**(\*\*对信号量的访问必须是互斥的原因:\*\*信号量<span style="color: #0b6e99;">`S`</span>是能够被多个进程共享的变量，多个进程都可以通过<span style="color: #0b6e99;">`wait()`</span>和<span style="color: #0b6e99;">`signal()`</span>操作对`S`进行读、写操作)
  对于<span style="color: #0b6e99;">单处理机环境</span>来说，在执行这两种操作时可以简单<span style="color: #0b6e99;">禁止中断</span>；
  对于<span style="color: #0b6e99;">多处理机</span>来说，若采用这种策略那么每个<span style="color: #0b6e99;">处理器的中断</span>都应该被禁止，否则在不同处理器上不同的运行进程可能会以任意不同方式一起交织执行，然而每个处理器中断的禁止是很困难的，且严重影响性能。因此<span style="color: #0b6e99;">多处理器系统</span>例如<span style="color: #e03e3e;">`SMP`</span><span style="color: #e03e3e;">系统</span>应该提供其他加锁技术，如<span style="color: #0b6e99;">`compare_and_swap`</span>或<span style="color: #0b6e99;">自旋锁</span>，以确保<span style="color: #0b6e99;">`wait()`</span>和<span style="color: #0b6e99;">`signal()`</span>原子执行。
- 还有一点，这里**并没有完全取消**<span style="color: #0b6e99;">忙等待</span>，只是将忙等待从<span style="color: #0b6e99;">进入区</span>移到<span style="color: #0b6e99;">临界区</span>，即将忙等待限制在操作<span style="color: #0b6e99;">`wait()`</span>和<span style="color: #0b6e99;">`signal()`</span>的临界区内。这些区比较短，因此临界区几乎不被占用，忙等待很少发生，而且所需时间极短。

1. 信号量机制实现进程互斥
   互斥是不同进程对同一信号量进行P、V操作实现的。

实现步骤:

- 分析并发进程的关键活动，划定临界区(如对临界资源打印机的访问应放在临界区)
- 设置**互斥信号量**`mutex`初值为1
- 在进入区`P(mutex)`——申请资源
- 在退出区`V(mutex)`——释放资源

```c
semaphore mutex = 1;  // 初始化信号量

P1() {
  ...
  P(mutex);   // 使用临界资源前加锁
  临界区;
  V(mutex);   // 使用完临界资源后解锁
  .....
}

P2() {
  ...
  P(mutex);   // 使用临界资源前加锁
  临界区;
  V(mutex);   // 使用完临界资源后解锁
  .....
}
```

注意:**对不同的临界资源设置不同的互斥信号量**；**P、V操作必须成对出现**，缺少`P(mutex)`操作就不能保证临界资源的互斥访问，缺少`V(mutex)`会导致资源永不释放，等待进程永远不会被唤醒；因此在互斥问题中，P、V操作要夹紧使用互斥资源的那个行为，中间不能有其他冗余代码。

1. 信号量机制实现同步
   进程同步:要让各并发进程按要求有序地推进。

实现步骤:

- 分析什么地方需要实现“同步关系”，即必须保证“**一前一后**”执行的两个操作(或两句代码)
- 设置**同步信号量S，初始为0；**
- 在“前操作”之后执行`V(S)`;
- 在“后操作”之前执行`P(S)`;
  示例:进程P2中的语句y要使用进程P1中语句x的运行结果，所以只有当语句x执行完成之后语句y才可以执行。

```c
semaphore S = 0;
p1(){
  	x; // 语句 x
  	V(S); // 告诉进程 P2，语句 x 已经完成
  	...
}

p2(){
  	P(S); // 检查语句 x 是否已经运行完成
  	y; // 检查 x 已完成，执行 y 语句
  	...
}
```

1. 信号量机制实现前驱关系(多级同步问题)
   每一对前驱关系都是一个进程同步问题(需要保证一前一后的操作)，因此

- 要为每一对前驱关系各设置一个同步信号量
- 在“前操作”之后对相应的同步信号量执行V操作
- 在”后操作“之前对相应的同步信号量执行P操作

### 管程

1. 引入<span style="color: #0b6e99;">管程</span>的原因:虽然<span style="color: #0b6e99;">信号量机制</span>足够好用，例如相比于<span style="color: #0b6e99;">锁</span>来说允许多个线程同时访问一个<span style="color: #0b6e99;">临界区</span>，只要<span style="color: #0b6e99;">count</span>符合条件即可。但是仍存在一些缺点，那就是真正使用起来比较困难，因为当我们需要解决的<span style="color: #0b6e99;">同步问题</span>越复杂，<span style="color: #0b6e99;">条件</span>越多，所需要的<span style="color: #0b6e99;">信号量</span>也就越多，需要更加地谨慎处理信号量之间的处理顺序，否则很容易造成<span style="color: #e03e3e;">死锁</span>，这点在后面的类似于<span style="color: #0b6e99;">生产者消费者问题</span>就能看出来。为此便产生了一种新的<span style="color: #0b6e99;">进程同步工具</span>———<span style="color: #0b6e99;">管程</span>。 <span style="color: #0b6e99;">管程</span>的特性保证了<span style="color: #0b6e99;">进程互斥</span>，无须程序员自己实现互斥，从而降低了<span style="color: #e03e3e;">死锁</span>发生的可能性。同时<span style="color: #0b6e99;">管程</span>提供了<span style="color: #0b6e99;">条件变量</span>，可以让程序员灵活地实现<span style="color: #0b6e99;">进程同步</span>。管程优于信号量之处在于，**所有的**<span style="color: #0b6e99;">**同步机制**</span>**都被限制在**<span style="color: #0b6e99;">**管程内部**</span>，因此，不但容易验证同步的正确性，而且易于检查出错误。此外如果一个<span style="color: #0b6e99;">管程</span>被正确得编写，则所有进程对受保护资源的访问都是正确的；而对于<span style="color: #0b6e99;">信号量</span>，只有当所有访问资源的进程都被正确地编写时，资源访问才是正确的。

![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418457907-2f9cd5ea-f272-4420-8b9a-decbd983e493-371362.png)

1. 管程的定义和基本特征

- <span style="color: #0b6e99;">管程的定义</span>:利用<span style="color: #0b6e99;">共享数据结构</span>抽象表示系统中的<span style="color: #0b6e99;">共享资源</span>，并将对该数据结构的操作定义为一组<span style="color: #0b6e99;">过程</span>。进程对共享资源的申请、释放等操作，都通过这组过程来实现。这组过程还能根据资源状态，允许或阻塞进程访问，从而确保每次仅有一个进程使用共享资源，实现<span style="color: #0b6e99;">进程互斥</span>。代表共享资源的数据结构以及操作它的一组过程，组成了<span style="color: #0b6e99;">**管程(monitor)**</span>。
- <span style="color: #0b6e99;">管程实现的一般方法</span>:收集对象/模块中的相关<span style="color: #0b6e99;">共享数据</span>，并定义访问这些共享数据的方法。
- 管程是一种特殊的软件模块（<span style="color: #0b6e99;">抽象数据类型</span>），采用面向对象思想封装了线程间的<span style="color: #0b6e99;">同步控制</span>，即将共享变量及其操作封装成具有接口的功能模块。进程通过调用管程来实现进程级并发控制，因此管程主要包含以下部分:
  - <span style="color: #0b6e99;">管程的名称</span>
    - **局部于管程的共享数据结构说明**；
    - **对该数据结构进行操作的一组过程（或函数）**；
    - **对局部于管程的共享数据设置初始值的语句**；
- 补充:管程包含<span style="color: #0b6e99;">入口等待队列</span>、一个<span style="color: #0b6e99;">锁</span>（控制整个管程代码的互斥访问）、0个或多个<span style="color: #0b6e99;">条件变量</span>（等待/通知信号量用于管理并发访问共享数据）。每个条件变量都拥有自己的等待队列及相应的出/入队操作。
  ![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418457933-de6285d6-294b-4944-8d5a-18e603575ab4-384994.png)
- 注意:<span style="color: #0b6e99;">入口等待队列</span>中的线程为**条件满足情况未知**或**曾经满足过条件**的线程，等待管程新一轮执行。而<span style="color: #0b6e99;">条件变量</span>的等待队列中的线程，需满足条件后才能重新回到入口等待队列。
- （可结合后面用管程解决生产者/消费者问题时，while/if语句的分析理解）
- <span style="color: #0b6e99;">管程的基本特性</span>:
  - **只有管程内定义的函数才能访问管程内的局部声明变量和形式参数。类似地，管程的局部变量只能由局部函数（过程）访问。**
    - 一个进程通过调用管程的一个过程（局部函数）进入管程；
    - **任何时刻，只能有一个进程在管程中执行，其余进程需等待管程可用时才能进入。**

1. 管程如何实现互斥与同步:
   对管程的实现互斥由编译器负责！在Java中，只要将关键字`synchronized`加入到方法声明中，Java保证一旦某个线程执行该方法，就不允许其他线程执行该类中的任何其他方法。通过给进程强加规定，管程可用提供一种互斥机制:管程中的数据变量每次只能被一个进程访问到。因此将代表某些临界资源的共享数据结构放在管程中，从而为访问这些资源提供了互斥机制。也可以理解为由等待队列+封装实现互斥。

管程通过使用**条件变量**提供对同步的支持，这些条件变量包含在管程中，并且只有在管程中才能被访问。**有两个函数可以操作条件变量**:

`x.wait()`:当x对应的条件不满足时，正在调用管程的进程调用x.wait()将自己阻塞，即插入到x条件的等待队列中，并释放管程。此时其他进程可以使用该管程。

`x.signal()`:x对应的条件发生了变化，则调用x.signal(),唤醒一个因x条件而阻塞的进程。

```c
Class condition {
  int numWaiting = 0; //统计有多少个线程处T等待队列中
  WaitQueue q;
}

Condition::Wait(lock){
  numWaiting++;
  Add this thread t to q;
  release(lock); //release()因为当前线程在睡眠，就必须把锁打开一下，以便入口等待队列的线程去执行，如果不release可能会造成死锁；
  schedule(); //调度，need mutex
  require(lock); //如果又被调度到了，则上个锁；
}

Condition::Signal() {
  if(numWaiting > 0){ //如果等待队列中有元素，那么就把队列的头元素取出来(并删掉)并唤醒wakeup
      Remove a thread t from q;
      wakeup(t); //need mutex
      numWaiting--; //注意，signal()仅在等待队列中有元素的时候才对numberWaiting执行(减法操作)，而信号量不一样，在P()和V()一定会对信号量进行加减操作，这也是二者的一个重要区别。
  }
}
```

1. 用管程解决生产者消费者问题的实例:

```c
classBoundedBuffer{
  ....
  Lock lock;
  int count = 0;
  Condition notFull,notEmpty;
}

BoundedBuffer::Deposit(c) {
  lock->Acquire();
  while(count==n){
      notFull.Wait(&lock);
  }
  Add c to the buffer;
  count++;
  notEmpty.Signal();
  lock->release();
}

BoundedBuffer::Remove(c) {
  lock->Acquire();
  while(count == 0){
      notEmpty.Wait(&lock);
  }
  Remove c from buffer;
  count --;
  notFull.Signal();
  lock->Release();
}
```

根据管程定义，只有一个线程能进入管程，所以一开始就上锁，在最后才解锁；这里和信号量是不一样的，信号量的互斥是紧紧靠着信号量的，而管程的互斥是在头和尾。注意，这个lock是管程的lock。

王道伪代码:

```c
monitor ProduceConsumer
  conditon notFull,notEmpty;  //管程中设置条件变量和等待/唤醒操作，以解决同步问题，这里注意条件变量和信号量不同
  int count = 0; //缓冲区的产品的数
  不要初始化

  //把产品item放入缓冲区
  void insert(Item item)      //由编译器负责实现互斥地进入管程中的过程(函数)
  {
      while(count==N) {       //缓冲区已经满了
          wait(notFull);      //要等待缓冲区为有空间时，再放入产品
      }
      count++;
      insert_item(item);
      while(count==1) {       //缓冲区不为空
          signal(notEmpty);   //通知remove缓冲区不为空
      }
  }

  //从缓冲区取出一个产品
  Item remove()
  {
      while(count==0) {       //缓冲区没有东西，为空
          wait(notEmpty);     //等待缓冲区里面不为空，再从中取出产品
      }
      count--;
      while(count==N-1) {     //若拿走一个产品后数量为N-1，则拿走之前缓冲区是满的
          signal(notFull);    //告诉insert缓冲区不为满了，可以放入产品了
      }
      return remove_item();
  }
end monitor;

      item=生产一个产品；
      ProducerConsumer.insert(item);
  }
}
```

注意:管程是一个编程语言概念，编译器必须要识别出管程并用某种方式对互斥做出安排。C、Pascal及多数其他语言都没有管程，这里的伪代码只是用来解释原理。

> OSTEP:对条件变量使用while（而不是if)

> 多线程程序在检查条件变量时，使用while循环总是对的。if语句可能会对，这取决于发信号的语义。因此，总是使用while，代码就会符合预期。
>
> 对条件变量使用`while`循环，这也解决了假唤醒（`spurious wakeup`）的情况。某些线程库中，由于实现的细节，有可能出现一个信号唤醒两个线程的情况。再次检查线程的等待条件，假唤醒是另一个原因。

1. **条件变量**:
   当一个进程进入管程后被阻塞，直到阻塞的原因解除时，在此期间，如果该进程不释放管程，那么其他进程无法进入管程，为此，将阻塞原因定义为**条件变量**condition.通常一个进程被阻塞的原因可以有多个，因此在管程中设置了多个条件变量。每个条件变量保存了一个等待队列，对条件变量只能进行wait和signal操作。

条件变量与信号量的比较:

- 相似点:条件变量的`wait/signal`操作类似于信号量的P/V操作，可以实现进程的阻塞/唤醒。
- 不同点:
  1. 条件变量是“没有值”的，仅实现了“排队等待”的功能；而信号量是有值的，信号量的值反映了剩余资源数，而在管程中，剩余资源数用共享数据结构记录。
  2. **条件变量的**`wait/signal`**操作与信号量不同，如果在管程中的一个进程发信号，但没有在这个条件变量上等待的任务，则丢弃这个信号**。
     注意:条件变量不仅存在于管程中，在多线程库中也是普遍存在的。Unix的多线程库`Pthread`也使用条件变量协调进程的同步。

## 经典同步问题

### 生产者—消费者(有界缓冲区)问题

- 应用场景:在多线程程序中，线程之间通常存在分工。常见模式包括部分线程为<span style="color: #0b6e99;">生产者</span>，部分线程为<span style="color: #0f7b6c;">消费者</span>。<span style="color: #0b6e99;">生产者</span>创建物品并添加到数据结构，<span style="color: #0f7b6c;">消费者</span>处理并删除它们。<span style="color: #d9730d;">事件驱动程序</span>是典型例子，如用户操作、数据到达等。<span style="color: #0b6e99;">生产者线程</span>创建事件对象并加入<span style="color: #6940a5;">事件缓冲区</span>，<span style="color: #0f7b6c;">消费者线程</span>从缓冲区取出并处理，这些消费者也叫“<span style="color: #6940a5;">事件处理程序</span>”。系统正常运行需满足以下<span style="color: #e03e3e;">同步约束</span>:
  - 在<span style="color: #6940a5;">缓冲区</span>中添加或删除项目时，缓冲区处于不一致状态，线程必须具有对缓冲区的<span style="color: #e03e3e;">独占访问</span>权限。
  - 当<span style="color: #0f7b6c;">消费者线程</span>到达且缓冲区为空时，需<span style="color: #e03e3e;">阻塞</span>，直到<span style="color: #0b6e99;">生产者</span>添加新项目。

> 系统中有一组<span style="color: #0b6e99;">生产者进程</span>和一组<span style="color: #0f7b6c;">消费者进程</span>。 <span style="color: #0b6e99;">生产者</span>每次生产一个<span style="color: #d9730d;">产品</span>放入<span style="color: #6940a5;">缓冲区</span>，<span style="color: #0f7b6c;">消费者</span>每次从缓冲区取出产品并使用。
> 生产者和消费者共享一个初始为空、大小为 <span style="color: #e03e3e;">`n`</span> 的缓冲区。

> **缓冲区没满**
>
> ![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418458308-8463c9f5-53d5-4203-a5ac-a90f785b1ef3-156532.png)
>
> **缓冲区不空**
>
> ![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418458851-f38ad71e-ab7c-452e-86a4-33eb40491102-194755.png)
>
> 缓冲区是临界资源， 各进程必须<span style="color: #e03e3e;">**互斥地访问**</span>。

- 伪代码分析:

```c
int n;
semaphore mutex = 1; // 互斥信号量, 实现对缓冲区的互斥访问
semaphore full = 0; // 同步信号量, 表示产品的数量, 也即非空缓冲区的数量
semaphore empty = n; // 同步信号量, 表示空缓冲区的数量

void producer() {
    while(true) {
        // 生产一个产品(数据);
        p(empty);   // 消耗一个空闲缓冲区
        p(mutex);   // 互斥关紧进入缓冲区
        // 将产品(数据)放入缓冲区;
        v(mutex);
        v(full);    // 增加一个产品
    }
}

void consumer() {
    while(true) {
        p(full);    // 消耗一个产品
        p(mutex);
        // 从缓冲区取出数据;
        v(mutex);
        v(empty);
        // 消费产品;
    }
}
```

注意:<span style="color: #e03e3e;">必须先对资源信号量</span>进行<span style="color: #0b6e99;">P操作</span>，再对<span style="color: #d9730d;">互斥信号量</span>进行<span style="color: #0b6e99;">P操作</span>。如果顺序颠倒，可能导致<span style="color: #e03e3e;">死锁</span>:如生产者进程先对<span style="color: #d9730d;">`mutex`</span>做<span style="color: #0b6e99;">P操作</span>后被阻塞，消费者进程由于<span style="color: #d9730d;">`mutex=0`</span>也无法进入临界区，二者相互等待，造成死锁。<span style="color: #0f7b6c;">V操作</span>不会导致此问题，因此顺序可调换。

- **生产者消费者问题解题模板及例题:**

> 生产者–消费者问题的解题步骤（思路）:（参考王道强化课)

> 1. <span style="color: #6940a5;">**分析进程类别**</span>:根据题意，区分有几类进程，每类进程对应一个函数。若进程是不断重复的可以加一个`while(true)`循环；
> 2. <span style="color: #6940a5;">**描述进程动作**</span>:在函数内部，用中文描述每一步动作；
> 3. <span style="color: #6940a5;">**添加PV操作**</span>:用中文描述每个PV操作的作用；
>
> - <span style="color: #d9730d;">**同步操作**</span>:每个动作开始前，判断是否需要消耗资源（如缓冲区空位或产品），需要时进行`P操作`，在产生资源的地方进行`V操作`；由于PV操作是成对出现的，能有效避免遗漏。
> - <span style="color: #d9730d;">**互斥操作**</span>:注意缓冲区的互斥访问，进入缓冲区前后分别加上`PV操作`。
>
> 1. <span style="color: #6940a5;">**定义信号量**</span>:所有PV操作完成后，定义相应信号量。
>
> - 对于<span style="color: #d9730d;">互斥信号量</span>，初值为`1`；
> - 对于<span style="color: #d9730d;">同步信号量</span>（前驱后继），初值一般为`0`；
> - 其他一般信号量根据题意设置，如缓冲区空位`empty = N`，产品数`full = 0`。若缓冲区空位为1，只需一个一般信号量，此信号量可兼作互斥信号量。
>
> 1. <span style="color: #6940a5;">**检查死锁风险**</span>:
>
> - <span style="color: #d9730d;">**连续P操作死锁检查**</span>:连续对一般信号量执行`P操作`（不含互斥信号量），如进程所需资源数大于1。根据死锁原理，进程获得的资源不会释放，满足`请求并保持`，若资源不足且进程互相占有对方所需资源，则会死锁（见题4）。<span style="color: #e03e3e;">如有死锁风险，可在连续P操作前后加互斥锁，使其一气呵成。</span>
> - <span style="color: #d9730d;">**非连续P操作死锁检查**</span>:进程需多个资源且需多步操作，资源获取与操作交错进行，容易产生死锁（见题8）。解决方法:将所有资源请求的`P操作`写在一起，转为连续P操作，用上述方法处理。
> - <span style="color: #d9730d;">**共享缓冲区死锁检查**</span>:多个进程共享同一缓冲区时，若某一进程推进过快，缓冲区可能被其产品占满，其他进程无法放入产品，产生死锁（见题6）。
>   如进程A生产A，进程B生产B，消费者需A和B各一个，缓冲区空位N。若全被A占满，消费者手中已有A但还需B，此时B放不进，发生死锁。
>   为避免死锁，不能让单一进程占满缓冲区。A最多放N-1个A，B同理。
>   **解决思路:**<span style="color: #0b6e99;">通常可转为两个虚拟缓冲区:A、B各有最大空位N-1。放产品时，需先检查真实缓冲区有无空位，再检查自己虚拟缓冲区有无空位，两者皆有时，才能入缓冲区。</span>

> 工人 2(){

>     }
> }
> ```
>
> 试分别用信号量与 PV 操作实现三名工人的合作，要求解中不含死锁.

**死锁分析**:注意，题目 3 是两个生产者进程各自使用自己的缓冲区；而这道题是两个生产者进程共用一个缓冲区，此时就必须要考虑两个进程推进谁快谁慢的问题了，因为如果其中一个进程太快，就会导致缓冲区很快被其中一种产品全部占满，从而发生死锁现象。现在就来考虑下面几种情形:

- 如果工人 1 速度很快，箱子很快就被车架占满了，工人 2 没法放车轮，工人 3 没法造车，产生死锁；
- 如果工人 2 速度很快，箱子很快就被车轮占满了，工人 1 没法放车架，工人 3 没法造车，产生死锁；
- 如果工人 1 速度很快，箱子很快就被车架占用了，只剩下一个空位，工人 2 放一个车轮，工人 3 只能获取一个车架和一个车轮，没法造车，产生死锁。
  解决办法:

对于工人 1，当他发现空位数只剩下两个的时候（即最多只能放N-2个车架），他就不能再放车架了，必须要让工人 2 放车轮；

对于工人 2，当他发现空位数只剩下一个的时候（即最多只能放N-1个车轮），他就不能再放车轮了，必须要让工人 1 放车架。

所以此时需要再构造两个虚拟的缓冲区，**把共享缓冲区问题转化为双缓冲区问题**:

```c
semaphore wheel = 0; // 箱子内车轮数量
semaphore mutex = 1; // 互斥访问箱子
semaphore frameMax = N-1; // 最多还能放几个车架
semaphore wheelMax = N-2; // 最多还能放几个车轮

工人 1(){
    while(1){
        加工一个车架;
        P(frameMax); // 车架数已达上限?
        P(empty);
        P(mutex);

        V(mutex);
        V(frame);
    }
}

工人 2(){
    while(1){
        加工一个车轮;
        P(wheelMax); // 车轮数已达上限?
        P(empty);
        P(mutex);
        车轮放入箱中;
        V(mutex);
        V(wheel);
    }
}

工人 3(){
    while(1){
        P(frame);
        P(mutex);
        箱中取出一个车架;
        V(mutex);
        V(empty);
        V(frameMax);

        P(wheel);
        P(wheel);
        P(mutex);
        箱中取出二个车轮;
        V(mutex);
        V(empty);
        V(empty);
```

1. **单生产者、单消费者、多类资源需求类问题**

> 某寺庙有小和尚和老和尚若干，有一个水缸，由小和尚提水入缸供老和尚饮用。水缸可以容纳 10 桶水，水取自同一口井中，由于水井口窄，每次只能容纳一个水桶取水。水桶总数为3个。每次入水、取水仅为一桶，且不可同时进行。试给出有关从缸取水、入水的算法描述。

![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418460530-eea8e498-fc2a-4741-8fa4-e5fbcaf2c3fa-605200.png)

**死锁分析**:两类进程都可能会出现死锁。原因在于，小和尚取桶、水井取水、往水缸倒水和检查的三个 P 操作不能一气呵成，先检查一类资源，再去占用，容易发生死锁；同理，老和尚取桶、从水缸取水也不能一气呵成。如果先检查所有的资源是否满足，再去占用资源（参考银行家算法），那就不会发生死锁。

事实上，我们可以将小和尚检查是否有桶、水井是否有空位、水缸是否有空位这三个 P 操作连在一起，也就是说，先让小和尚一并检查这三类资源是否满足需求，如果满足，再让他占用资源，完成下面的操作。这个原理，其中之一就是**破坏请求保持条件**，在进程运行前一次申请完所有的资源；其中之二是银行家算法的思想——避免死锁。对老和尚也是一样的道理。当然，这些连续的 P 操作必须要加上一个互斥大锁。

```c
semaphore tong = 3; // 表示有多少个桶可以用, 初始值为3;
semaphore jing = 1; // 互斥访问水井
semaphore gang = 1; // 同上, 互斥访问水缸
semaphore gang_full = 0; // 表示水缸中水的桶数
semaphore gang_empty = 10; // 用于表示水缸中剩余空间能容纳的水的桶数;
semaphore mutex = 1; // 一一把互斥大锁, 用于一气呵成地完成多个资源的申请工作;

小和尚(){
    while(1){
        P(mutex); // 互斥大锁
        P(tong);
        P(jing);
        P(gang_empty);
        V(mutex);
        到水井打一桶水;
        V(jing);
        P(gang);
        往缸里倒水;
        V(gang);
        V(gang_full);
        V(tong);
    }
}

老和尚(){
    while(1){
        P(mutex);
        P(tong);
        P(gang_full);
        V(mutex);
        P(gang);
        从水缸打一桶水;
        V(gang);
        V(gang_empty);
        V(tong);
    }
}
```

### 读者—写者问题(真题尚未考过)

> 问题描述:有读者和写者两组并发进程，共享一个文件，当两个或两个以上的读进程同时访问共享数据时不会产生副作用，但若某个写进程和其他进程(读进程或写进程)同时访问共享数据时则可能导致数据不一致的错误。因此要求:

> - 允许多个读进程可以同时对文件执行读操作；(注意这里的读者进程与消费者进程不同，读者进程在读数据后并不会改变数据，而消费者则会将当前数据清除)
> - 同一时刻只允许一个写者往文件中写信息；(两个及以上写进程同时共享数据可能会导致数据错误覆盖的问题)
> - 任一写者在完成写操作之前不允许其他任何进程工作；
> - 写者执行写操作之前，应让已有的读者写者全部退出； (读进程与写进程同时共享数据，可能导致读出的数据不一致的问题)

- 应用场景:适用于并发线程读取和修改数据结构、数据库或文件系统的任何情况。 在写入或修改数据结构时，通常需要禁止其他线程读取，以防止读者线程中断正在进行的修改并读取不一致或无效的数据。与生产者 - 消费者问题一样，解决方案是不对称的。 读者和写者在进入关键部分之前执行不同的代码。 同步约束是:
  1. 任何数量的读者可以同时进入关键部分。
  2. 写者必须拥有对关键部分的独占访问权。
     换句话说，当任何其他线程（读者或者写者）在那里时，写者不能进入临界区；而当写者在那里时，其他线程都不可以进入。

这里的排除模式可以被称为**分类互斥（categorical mutual exclusion）**。 临界区中的线程不一定排除其他线程，但是在临界区中存在一个类别会排除其他类别。

通用解题模板:读者写者问题，其本质就是连续多个同类进程访问同一个临界资源的问题。

第一个进程开始访问临界资源前，需要对资源加上互斥锁，后面的进程再访问时就不用再对资源加互斥锁了，直到最后一个进程访问完后，发现自己是最后一个进程，就解锁互斥锁。这就像一种情况:第一个人进房间时必须顺手开门，后面进来的人和离开的人就不用开门，直到最后一个人离开房间时才需要顺手关门。

代码的通用模板是“三段式”，如下:

```c
int count = 0; // 记录正在访问的进程数量
semaphore rw = 1; // “完成事件”的互斥锁
semaphore mutex = 1; // 变量 count 的互斥锁

Process(){
    while(1){
        P(mutex);
        count++; // 访问资源的进程数量加 1
        if (count == 1){ // (1) 如果发现自己是第一个访问的进程，需要负责加锁
            P(rw);
        }
        V(mutex);

        完成事件; // (2) 访问临界资源、完成临界事件

        P(mutex);
        count--; // 访问完毕，访问资源的进程数量减 1
        if (count == 0){ // (3) 如果发现自己是最后一个访问的进程，需要负责解锁
            V(rw);
        }
        V(mutex);
    }
}
```

1. 实现方法一:读者优先

> 基于读者优先策略的方法，只要有一个读者处于活动状态，后来的读者都会被接纳。如果读者源源不断地出现地话，那么写者就始终处于阻塞状态，可能会“饿死”。

```c
semaphore rw = 1; // 用于实现写进程和其他进程对共享资源的互斥访问;
int Rcount = 0; // 记录当前有几个读进程在访问共享资源;
semaphore rmutex = 1; // 用于保证对Rcount变量的互斥访问; // 从而一气呵成完成对Rcount变量的检查和赋值操作;

void reader(){
    while(true){
        P(rmutex);
        // 各读进程互斥访问Rcount变量;
        if(Rcount == 0){
            P(rw);
            // 由第一个读进程负责“上锁”，这句是实现“读优先”的关键，以及阻止写进程写;
        }
        Rcount ++;
        V(rmutex);

        读取文件;

        P(rmutex);
        // 各读进程互斥访问Rcount变量;
        Rcount --;
        if(Rcount == 0){
            V(rw);
            // 最后一个离开的读进程负责“解锁”，允许写进程写;
        }
        V(rmutex);
    }
}

void writer(){
    while(true){
        P(rw);
        写文件;
        V(rw);
    }
}
```

假设每个读者的读操作都耗时较长，读者写者到达的顺序是:`读者1---读者2---读者3---写者A---读者 4---写者 B---读者 5`，则:

- 读者 1、读者 2、读者 3 到达，rw加锁，开始读；
- 写者 A 到达，但是读者还在读，未释放 rw 锁，因此不能写；
- 读者 4 到达，可以开始读；
- 写者 B 到达，但是读者还在读，未释放 rw 锁，因此不能写；
- 读者 5 到达，可以开始读；
  等到读者们都读完，释放 rw 锁，写者才可以开始写。

1. 实现方法二:写者优先

> 所谓写者优先，即:当有读者进程正在执行，写者进程发出申请，这时应该拒绝其他读者进程的请求，等待当前读者进程结束后立即执行写者进程，只有在无写者进程执行的情况下才能够允许读者进程再次执行。

> 为此在读者进程的基础上，增加信号量read值为1，用来禁止所有的读进程；增加一个写者进程的计数器，初值为0，用于实现写优先；另外自然也要为写者进程的计数器设置一个互斥信号量用来互斥访问；因此，伪代码如下:

```c
semaphore read = 1; // 互斥信号量，用于给读者“上锁”
semaphore write = 1; // 互斥信号量，用于给写者“上锁”
semaphore rmutex = 1; // 用于实现对rcount的互斥访问
semaphore wmutex = 1; // 用于实现对wcount的互斥访问
int rcount = 0, wcount = 0; // 读者、写者的数量

void reader(){
    while(true){
        P(read); // 每个读者进程进入到之前先对read上锁;
        P(rmutex);
        rcount++;
        if(rcount == 1) P(write); // 第一个开始读的进程对写进程上锁;
        V(rmutex);
        V(read); // 每个读者正式读之前先对read解锁，这是实现多个读进程可以同时访问共享资源的关键;
        读文件;
        P(rmutex);
        rcount --;
        if(rcount == 0) V(write); // 最后一个读完的读者对写者解锁;
        V(rmutex);
    }
}

void writer(){
    while(true){
        P(wmutex);
        wcount ++;
        if(wcount == 1) P(read); // 第一个到达的写者对读者上锁，这步是实现“写优先”的关键
        V(wmutex);
        P(write); // 每个写者写之前都要P(write)，保证写者之间互斥，同时也能保证若当前有读者在读，那么写者等待
        写文件;
        V(write);
        P(wmutex);
        wcount --;
        if(wcount == 0) V(read); // 最后一个写者写完之后对读者解锁;
        V(wmutex);
    }
}
```

> 注意，这里 read 的作用，开始有多个读者读数据，它们全部进入读者队列，此时来了一个写者，执行了 P(read) 之后，后续的读者由于阻塞在 read 上，都不能再进入读者队列，而写者到来，则可以全部进入写者队列，因此保证了写者优先。

> 同时，第一个写者执行了 `P(read)` 之后，也不能马上开始写，必须等到所有进入读者队列的读者都执行完读操作，通过 `V(write)` 唤醒写者的写操作。

假设每个读者的读操作都耗时较长，读者写者到达的顺序是:`读者1---读者2---读者3---写者A---读者 4---写者 B---读者 5`，则:

- 读者 1、读者 2、读者 3 到达，Write 加锁，开始读；
- 写者 A 到达，Read 加锁，但是读者还在读，Write 锁仍未释放，因此不能写；
- 读者 4 到达，Read 锁仍未释放，不能开始读；
- 写者 B 到达，Write 锁仍未释放，因此不能写；
- 读者 5 到达，Read 锁仍未释放，不能开始读；
- 等到读者 1 到 3 都读完，释放 Write 锁，写者 A 才可以开始写，写完后 Write 解锁。由于写者 A 不是最后一个写进程，因此 Read 不解锁；
- 写者 B 进行写操作，写完后 Write 解锁，由于写者 B 是最后一个写进程，因此 Read 解锁；
- 读者 4、读者 5 依次进行读操作。

1. 实现方法三:读写公平法
   公平策略:

- 优先级相同；
- 写者、读者互斥访问；
- 只能一个写者访问临界区；
- 可以有多个读者同时访问临界资源；

> 为实现读写公平，我们设置一个互斥信号量queue,其作用是让读者和写者进行排队，当有reader进程执行时，queue = 0 ,因此writer进程会进入等待，直到queue变为1；当writer进程执行时同理；因此，我们借助queue实现了读写进程的优先级平等。

<details><summary>queue版本:这是一个非常典型的“读者无饥饿、写者无饥饿、弱公平”模式，但它**不是严格 FIFO 公平**。</summary>

```c
semaphore rw = 1;
int count = 0;
semaphore mutex = 1;
semaphore queue = 1; // 用于实现公平竞争，这里可以将其理解为1个队列，当资源不可访问时，无论读者还是写者都需要排队;

void reader(){
    while(true){
        P(queue);
        P(mutex);
        count ++;
        if(count == 1) P(rw);
        V(mutex);
        V(queue); // 这里释放一下否则无法实现多个读进程同时进入临界区;导致:
//读者已经到达 rw 门口，但仍然允许“后到达的读者”继续排队并进入读区.写者可能遭遇“读者波浪式插队”。

        读文件;
        P(mutex);
        count --;
        if(count == 0) V(rw);
        V(mutex);
    }
}

void writer(){
    while(true){
        P(queue); // 即使读进程在进入临界区之前将queue恢复，
        //这里可以执行下去，但是下一步无法执行，依旧会阻塞住，
        //从而实现当有读进程的时候写者不能进去;
        P(rw);
        写进程;
        V(rw);
        V(queue);
    }
}
```

# queue 版本是 **弱公平**，并不保证严格 FIFO

为什么？

核心在于这段:

```plain
P(queue)
P(mutex)
count++
if(count == 1) P(rw)
V(mutex)
V(queue)   <-- 读者在进入读区前释放 queue


```

释放 queue 会导致:

### 读者已经到达 rw 门口，但仍然允许“后到达的读者”继续排队并进入读区

这意味着:

- 写者被阻塞在 P(queue)
- 但读者不断地 P(queue) / V(queue)
- 成百上千的读者仍然可能源源不断进入
  读者虽然不会无限制饿死写者，但:

### 写者可能遭遇“读者波浪式插队”。

这不是严格的 FIFO，而是“只要当前存在读者，写者永远必须等待读者完全退出”。

因此它不是严格的队列语义。

```c
semaphore gate = 1;     // FIFO 关卡，所有线程先来这里排队
semaphore rw = 1;       // 控制读写互斥
semaphore mutex = 1;    // 保护 count

    while (true) {
        P(gate);         // 进入全局公平队列
        P(mutex);
        count++;
        if (count == 1)
            P(rw);        // 第一个读者锁住 rw
        V(mutex);
        V(gate);         // 释放 gate 让后续线程排队进入

        // ---- 临界区:读 ----
        read();

        P(mutex);
        count--;
        if (count == 0)
            V(rw);        // 最后一个读者释放 rw
        V(mutex);
    }
}
writer() {
    while (true) {
        P(gate);   // 进入公平队列
        P(rw);     // 独占访问
        // ---- 临界区:写 ----
        write();
        V(rw);
        V(gate);
    }
}
```

<details><summary>gate版本分析</summary>

# 一、为什么这是严格公平？

关键点:

### 1）gate 是一个“巨型 FIFO 等待队列”

所有线程（读者/写者）都要:

```plain
P(gate)
```

意味着:

- 到达顺序由 gate 决定
- gate 永远只允许一个线程进入“资源竞争阶段”
- 后到达的读者/写者必须排队
- 没有人能插队
  这是绝对公正的排队机制。

***

### 2）读者进入后立即 V(gate) 但不破坏公平性

许多人会误以为**读者提前放 gate 会破坏公平性**，但实际上:

**读者只有在已经获得“进入资源竞争的顺序权”后才释放 gate**，这不会改变排队顺序。

gate 的语义是:

“你排队排到我，现在轮到你进入资源竞争阶段。”

读者进入后:

- 它不阻塞后续线程排队
- 后续线程仍然要遵循 gate 的 FIFO 顺序
- gate 的队列顺序已经确定，不会因为读者释放 gate 而改变
  所以公平性仍然严格成立。

写者永远不能被新读者插队。

***

### 3）rw 确保写者独占 / 多读者共享

- 第一个读者 P(rw)
- 最后一个读者 V(rw)
- 写者独占 rw
  rw 不承担公平，而是单纯负责互斥。

公平完全由 gate 确保。

***

# 二、总结（可直接背下来）

**严格公平读写锁 = gate + rw + mutex + count**

- **gate**:排队公平（FIFO）
- **rw**:读写互斥
- **mutex**:保护 count
- **count**:读者数量
  特点:
- 无插队
- 无饥饿
- 读者并发
- 写者独占
- 到达顺序严格遵守
- 工业级公平性
  这是操作系统教材与实际系统中认可的最标准、最稳健的**完美公平读写锁模板**。

1. **万能模板 1——无等待上限，服务人员可休息**

> 题目:店里有 N 名服务人员，没有顾客时服务人员休息，有顾客时就叫号。顾客到店时，需要先取号，并叫醒一名休息的服务人员（如果有），并等待叫号。

**【解题思路】**:本题类似于生产者消费者问题，顾客是生产者，生产顾客资源；服务人员是消费者，消费顾客资源。反过来，服务人员是生产者，生产服务人员资源；顾客是消费者，消费服务人员资源。所以可以按生产者消费者的思路来解答。

服务人员叫号后，意味着有一个服务人员前来提供服务，可视为生产了一个服务人员；顾客取号后，意味着多了一名顾客在等待，可视为生产了一名顾客。而取号和叫号类似于放入缓冲区的操作，需要一个互斥锁。

```c
semaphore customer = 0; // 顾客资源数
semaphore server = 0; // 服务人员资源数
semaphore mutex = 1;

Server(){
    while(1){
        P(customer); // 开始干活前先消耗一个顾客资源, 若无顾客, 则阻塞等待(即睡眠休息)
        P(mutex);
        叫号;
        V(mutex);
        V(server);
        提供服务;
    }
}

Customer(){
    P(mutex);
    取号;
    V(mutex);
    V(customer);
    P(server); // 顾客被服务前占用一个服务员资源, 若无空闲服务员, 则阻塞等待;
    被服务;
}
```

1. **万能模板 2——有等待上限，服务人员可休息**

> 店里有 N 名服务人员，没有顾客时服务人员休息，有顾客时就叫号。店里有 M 个空位。顾客到店时，需要先检查是否 M 个位置被其他顾客都占用了，若是，则离店；若否，则占用一个位置取号等待，并叫醒一名休息的服务人员（如果有），并等待叫号。

【**解题思路**】可以先在上题的基础上增加一个变量 `waiting`，记录当前正在等待的顾客数。当顾客取号后，顾客等待数量加 1,；当服务人员叫号后，顾客等待数量减 1，然后只需在顾客进程加入一个判断，若顾客等待数量超过上限，则直接离店即可，代码如下:

```c
semaphore customer = 0; // 顾客资源数
semaphore server = 0; // 服务人员资源数
semaphore mutex = 1; // 互斥访问临界变量waiting
int waiting = 0; // 正在等待的顾客数量

Server_i(){ // n个服务员进程
    while(1){
        P(customer);
        P(mutex); // 互斥访问waiting变量
        叫号;
        waiting--;
        V(mutex);
        V(server);
        提供服务;
    }
}

Customer(){
    P(mutex);
    if (waiting < M){ // 若有空位则坐下等待
        取号;
        waiting++;
        V(mutex);
        V(customer);
        P(server);
        被服务;
    }
    else{ // 人满
        V(mutex);
        离店;
    }
}
```

1. **万能模板 3——有等待上限，服务人员忙等**

> 店里有 N 名服务人员，没有顾客时服务人员也不可以休息，必须“忙等”，有顾客时就叫号。店里有 M 个空位。顾客到店时，需要先检查是否 M 个位置被其他顾客都占用了，若是，则离店；若否，则占用一个位置取号等待，并叫醒一名休息的服务人员（如果有），并等待叫号。

【**解题思路**】在没有顾客时，服务人员忙等，不断询问有没有顾客，所以可以在上题基础上，在服务人员进程里加入判断顾客数量的语句。如果有顾客，则按之前的操作进行；如果没有顾客，则直接进行下一轮循环。因此，**对顾客资源的 P 操作就不需要了，因为 P 操作会引发阻塞或休息**。如下:

```c
semaphore server = 0; // 服务人员资源数
semaphore mutex = 1;
int waiting = 0; // 正在等待的顾客数量

Server(){
    while(1){
        P(mutex); // 互斥访问waiting变量
        if (waiting > 0){
            // P(customer); // 这句去掉, waiting 是这条 P 操作的无阻塞版本, 用以实现服务人员的忙等
            叫号;
            waiting--;
            V(mutex);
            V(server);
            提供服务;
        }
        else{
            V(mutex);
            continue;
            什么也不做, 进入下一轮循环;
        }
    }
}

Customer(){
    P(mutex);
    if (waiting < M){
        取号;
        waiting++;
        V(mutex);
        P(server);
        被服务;
    }
    else{
        V(mutex);
        离店;
    }
}
```

1. **万能模板 4——座位已满后顾客仍继续等待，服务人员可休息**

> 店里有 N 名服务人员，没有顾客时服务人员休息，有顾客时就叫号。

> 店里有 M 个空位。顾客到店时，需要先检查是否 M 个位置被其他顾客都占用了，若是，则等待座位空余(即先等空位再等叫号)；若否，则占用一个位置取号等待，并叫醒一名休息的服务人员（如果有），并等待叫号。

【**解题思路**】把前面的变量`waiting`变为信号量 `empty`即可，用来记录店里的空位，这样就可以起到阻塞等待的作用。

```c
semaphore customer = 0; // 顾客资源数
semaphore server = 0; // 服务人员资源数
semaphore empty = M;
semaphore mutex = 1;

Server(){
    while(1){
        P(customer);
        P(mutex);
        叫号;
        V(mutex);
        V(server);
        V(empty); // 释放一个店里的空位
        提供服务;
    }
}

Customer(){
    P(empty); // 店里有空位吗? 若有, 空位-1, 否则阻塞, 等待有空位再坐上去等待叫号
    P(mutex);
    取号;
    V(mutex);
    V(customer);
    P(server);
    被服务;
}
```

> 小结:

> - 大家在学习这部分内容的时候，只需把模板 1 的思路记下来即可，其余三个都是从第一个模板延伸而来。做题时，先把模板 1 默写出来，然后在此基础之上按题意进行修修补补。另外是不是有人发现了，这些代码跟服务人员的数量是不是没有关系的？因为我们模板的服务人员进程一共有 N 个，一个进程对应一个服务人员（当然也可以一个进程对应 N 个服务人员，需要额外再加一个记录服务人员的信号量），以后做这种题可以直接无视服务人员的数量，这是冗余条件。
> - 以上这些模板**都没有满足先来先服务**，即不能按照顾客到来的顺序为他们提供服务，这是因为当理发师进程`V(server)`后，任意一个顾客进程都有可能继续执行。解决方案是采用名为`queue`的信号量队列，具体操作见[此专栏](https://blog.csdn.net/booksyhay/article/details/82840877)。408一般不会要求先来先服务，这个不用过多了解。

### 哲学家进餐问题

> 题目描述:一张圆桌上坐着五名哲学家，在每两名哲学家中间放着一根筷子，哲学家们的生活方式只做两件事:思考和进餐。饥饿时哲学家必须同时拿起两只筷子时才能进餐，进餐完毕后，放下筷子，进行思考。如果筷子被紧挨着的一名哲学家使用着，则不能争抢，必须等待，当这名哲学家就餐完毕后，放下筷子，才能使用。

**该类题目特点:只有一类进程，要占用多种资源才能运行；**

**解题思路探究**:在哲学家进餐问题中，我们解决死锁的方法有3种:

1. **限制并发进程数**:例如限制同一时间内只能有一个哲学家进餐(**虽然通用，但是并发度不高，**
   **示意图:**

![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418463247-da75aa47-8392-4aea-8da4-6c17fd5b4cb4-729832.png)

```c
semaphore chopstick[5] = {1,1,1,1,1};
semaphore mutex = 1;

void Pi(int i){   // 哲学家 i
    while(1){
        P(mutex);
        P(chopstick[i]);               // 去拿左边的筷子
        P(chopstick[(i+1) % 5]);       // 去拿右边的筷子
        V(mutex);

        // 进餐
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);

        // 思考
    }
}
```

1. **限制申请资源的顺序**:奇数号哲学家必须先拿右手边的筷子，偶数号哲学家必须先拿左手的筷子(**不通用，不建议使用，了解即可**)
   **示意图**:

![](https://cos.izumichan16.cn/408note/OS/qEmfZepwiZJysDJ7/1718418463798-b5554e68-0ba1-4ea3-b078-73a125de2f29-581156.png)

```c
semaphore chopstick[5] = {1,1,1,1,1};

void Pi(int i){    // i为哲学家编号
    while(1){
        // 思考；
        if(i % 2 == 0){
            P(chopstick[i]);             // 去拿左边的筷子；
            P(chopstick[(i+1) % 5]);     // 去拿右边的筷子；
        }else{
            P(chopstick[(i+1) % 5]);
            P(chopstick[i]);
        }

        // 进餐；
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);
    }
}
```

上面的程序，在 P 操作时，根据哲学家的编号不同，拿起左右两边叉子的顺序不同。另外，V 操作不会阻塞的。这样可以避免死锁，并且可以有两个哲学家同时进餐。

1. **让进程一口气取得所有资源，再开始运行**。
   即仅当一个哲学家左右两边的筷子都可用时才允许哲学家拿筷子。代码见例题1.

> 其中方法二适用范围很窄，很难迁移到其他的类哲学家进餐问题，而另外两种方法的思想可以迁移到大多数这种类似的问题以解决“死锁”，这里我们采用最后一种思想:破坏“请求并保持”条件，让进程一口气获得所有所需的资源。

> 通用解题模板:

> - step1: **先定义一把大互斥锁**`semaphore lock = 1`;
> - step2: **定义资源数** :比如，a 资源有 9 个，b 资源有 8 个，c 资源有 5 个，则:
>
> ```c
> int a = 9;
> int b = 8;
> int c = 5;
> // 分别表示各自的剩余数量
> ```
>
> - step3: **默写代码模板**:
>   代码思路:
>   - **申请资源**:
>     - 进程先检测目前资源总数满不满足自身的需求。
>     - 若满足，则一气呵成地把所需要的资源全部占用。然后开始完成操作
>     - 若不满足，则忙别的事，然后进行下一轮检测。
>   - **归还资源**:
>     - 使用完资源后，进程也需要一气呵成地把所需要的资源全部归还。
>
> ```c
> Process(){
>     while(1){
>         P(Lock);
>         if (所有资源都够){ // 资源足够
>             所有资源数减少;
>             取xxx资源; // 根据题目每类资源需要多少直接将所有的int值减少，一口气拿走所有所需的资源
>             V(Lock);
>             break; // 已获得所需资源，跳出while循环，开始完成操作
>         }
>         else{
>             V(Lock); // 资源不够，解锁，再继续循环尝试;
>         }
>     }
>     
>     完成操作; // 做该进程需要做的事
>     
>     P(Lock);
>     一口气归还所有资源，所有资源数int值增加;
>     V(Lock);
> }
> ```
>
> **这种解题思路即:破坏“请求和保持”条件**，采⽤“**静态分配**”的思想，让进程⼀⼝⽓获得所有资源，再开始运⾏（可参见生产者消费者模型的“老和尚喝水、小和尚取水”的问题，那道题在进程开始操作前先连续 P 操作申请资源，全部申请完资源后再执行操作），如果不采用`int`
>
> ```c
> Process(){
>     while(1){
>         P(lock);    // 申请资源
>         P(资源1);
>         P(资源2);
>         P(资源3);
>         ...
>         V(lock);
>         完成操作;
>
>         P(lock);    // 归还资源
>         V(资源1);
>         V(资源2);
>         V(资源3);
>         ...
>         V(lock);
>     }
> }
> ```

> 经典版哲学家进餐问题

> # 经典哲学家问题最优化评析
>
> ## 为什么说这是“最优化”，不是“另一种写法”
>
> 我们从 **408 的三个核心评价维度** 来看。
>
> ***
>
> ### ① 死锁:结构性消除（不是“碰运气”）
>
> `room = 4` 的含义是:
>
> - 5 个哲学家
> - **最多 4 个**同时尝试拿筷子
>   这直接导致一个不变量:
>
> > 系统中永远至少剩下一根筷子是空闲的
>
> 于是:
>
> - 不可能形成“5 人各拿一根筷子互相等待”
> - **循环等待条件被永久破坏**
>   📌 这是教科书级的死锁避免，而不是临时规避。
>
> ***
>
> ### ② 等待方式:阻塞，而不是忙等（本质差异）
>
> 在你的原始方案中:
>
> ```c
> while(1){
>     P(lock);
>     if (能吃) break;
>     V(lock);
> }
>
>
> ```
>
> 这是 **CPU 主动轮询**。
>
> 而在最优方案中:
>
> ```c
> P(chopstick[i]);   // 拿不到 → 阻塞
>
>
> ```
>
> 特点是:
>
> - 不消耗 CPU
> - 等待由内核调度
> - 资源释放 → 精确唤醒
>   📌 这正是信号量存在的根本理由。
>
> ***
>
> ### ③ 并发性:最大化而不是保守化
>
> 对比一下:
>
> 在 5 个哲学家的场景中:
>
> - **理论上最多 2 人同时进餐**
> - 最优方案恰好达到这个上限
>   这说明:
>
> > 该方案在安全性与并发性之间达到了最优平衡

```c
semaphore room = 4;            // 最多 4 个哲学家同时尝试取筷子
semaphore chopstick[5] = {1, 1, 1, 1, 1};

Process(i){
    while (1) {
        P(room);                       // 进入取筷子阶段（破坏循环等待）

        P(chopstick[i]);               // 取左筷子
        P(chopstick[(i+1) % 5]);       // 取右筷子

        吃饭;

        V(chopstick[(i+1) % 5]);       // 归还右筷子
        V(chopstick[i]);               // 归还左筷子

        V(room);                       // 离开取筷子阶段
    }
}

```

> 加强版哲学家问题（1）:有 n（n ≥ 3）位哲学家围坐在一张圆桌边，每位哲学家交替地就餐和思考。在圆桌中心有 m（m ≥ 1）个碗，每两位哲学家之间有一根筷子。每位哲学家必须取到一个碗和两侧的筷子后，才能就餐，进餐完毕，将碗和筷子放回原位，并继续思考。 为使尽可能多的哲学家同时就餐，防止出现死锁现象。请使用信号量的 P、V 操作 \[wait()、signal() 操作] 描述上述过程中的互斥与同步，并说明所用信号量及初值的含义。

> # 加强版问题（1）最优解剖析
>
> ### 1️⃣ 忙等被彻底消除（这是本质改进）
>
> 在你的原代码中:
>
> - 资源不足 → 释放 lock → 立刻重试
> - 本质是 **CPU 忙等**
>   在优化方案中:
> - `P(chopstick)` / `P(bowl)` 失败 → **进程阻塞**
> - 直到资源真正可用才被唤醒
>   📌 这正是信号量存在的根本意义。
>
> ***
>
> ### 2️⃣ 死锁避免机制从“人为检查”升级为“结构性保证”
>
> 你的原方案是:
>
> > 通过一次性检查全部资源 + 大锁，避免死锁
>
> 优化方案采用的是经典结论:
>
> > 只要最多 n−1 个哲学家同时拿筷子，就不可能形成环路等待
>
> 原因很直观:
>
> - 即使 n−1 人各拿一根筷子
> - 仍然至少有 1 根筷子空闲
> - 至少有 1 人可以拿到两根筷子继续执行
>   这在 408 中属于**可以直接背结论的模型**。
>
> ***
>
> ### 3️⃣ 临界区粒度大幅缩小，并发性显著提升
>
> 原方案:
>
> - 所有哲学家
> - 所有资源
> - 全部串行化在 `lock` 下
>   优化方案:
> - 只有**同一根筷子**存在互斥
> - 不同哲学家可并行吃饭（只要资源允许）
>   这在系统层面意味着:
> - 更高吞吐率
> - 更少无意义等待
> - 更贴近真实操作系统设计
>
> ***
>
> ### 4️⃣ 碗（bowl）的建模是“教科书级正确”的
>
> ```c
> semaphore bowl = m;
> ```
>
> 这行代码本身就是一个标准答案:
>
> - 碗是 **可并发使用、数量有限** 的资源
> - 用计数信号量直接表达
> - 无需额外锁、无需判断
>   相比你原来的:
>
> ```c
> int bowl;
> P(lock);
> if (bowl > 0) ...
> ```
>
> 这是**抽象层级上的跃迁**。

```c
semaphore room = n - 1;      // 限制最多 n-1 个哲学家同时进入取筷子阶段
semaphore chopstick[n];     // 每根筷子一个二元信号量
semaphore bowl = m;         // 碗是计数信号量

Process(i){
    while (1) {
        P(room);                // 进入“进餐准备区”，避免死锁

        P(chopstick[i]);        // 取左筷子
        P(chopstick[(i+1)%n]);  // 取右筷子
        P(bowl);                // 取一个碗

        吃饭;

        V(bowl);                // 归还碗
        V(chopstick[(i+1)%n]);  // 归还右筷子
        V(chopstick[i]);        // 归还左筷子

        V(room);                // 离开准备区
    }
}
```
